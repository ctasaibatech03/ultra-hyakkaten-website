# kokai: お店のサイトを公開する

必ず次の1〜5の順に進める。ユーザーへの説明はやさしい日本語で、短くする。

## 1. 変更の一覧と説明

- `git status --short` と `git diff HEAD --stat` で、まだコミットしていない変更（新規・変更・削除）を集める。
- 新規ファイル（`??`）は中身を軽く見る。フォルダなら中のファイルも確認する。
- 次の形で出す。
  - ファイルごとに1行で「何が変わったか」
  - 最後に全体の一言まとめ
- 変更が何もなければ「公開する変更はありません」と伝えて終了する。

## 2. 秘密のファイルのチェック

コミット対象になるファイルに、秘密が入っていないか確かめる。

- ファイル名: `.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa*`, `credentials*`, `.mcp.json`, `*.sqlite`, `*.db` など。
- 中身: 変更差分と新規ファイルを `API_KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `DATABASE_URL`, `re_`（Resendキー）, `sk-`, `postgres://` などで検索する。
- `git check-ignore -v <file>` で、`.env` などが `.gitignore` で除外されているか確認する。
- すでに過去のコミットに入っていないかも `git ls-files` で確認する。
- 結果を「問題なし」か「危険なもの」で報告する。
- 危険なものがあれば、**公開を止める**。`.gitignore` への追加や、中身の削除を提案し、直るまで3に進まない。
- `.gitignore` が社内資料として除外しているファイル（設計書など）は、公開しないのが正しい。コミットに含めない。

## 3. 確認して待つ

「この内容で公開してよいですか？（ok で公開します）」と聞く。

- ユーザーが `ok` と言うまで、**何もコミット・プッシュしない**。
- 修正の希望や「やめる」なら、それに従う。曖昧な返事は okとみなさず、もう一度聞く。

## 4. コミットとプッシュ

okをもらったら実行する。

1. 2で確認したファイルだけを名前で `git add` する（`git add -A` と `git add .` は使わない）。
2. コミットメッセージは、変更内容が分かる日本語の1行（このリポジトリの過去のコミットと同じ書き方）。末尾にシステムから指示された Co-Authored-By の行を付ける。
3. `git push origin <現在のブランチ>` を実行する。
4. 失敗したら（認証・競合など）、原因をやさしく説明して止まる。`--force` は使わない。

## 5. 公開URLとQRコード

このサイトは Vercel で公開されている（`vercel.json` あり）。GitHub へのプッシュで自動デプロイされる。

1. 公開URLを調べる。順に試す。
   - `.claude/skills/kokai/url.txt` があれば、その中のURL。
   - `vercel project ls` / `vercel inspect` などで分かればそれ。
   - どれも無ければ、ユーザーに公開URLを1回だけ聞き、`.claude/skills/kokai/url.txt` に保存する（次回から聞かない）。
2. URLを表示する。デプロイ反映まで1〜2分かかることを一言添える。
3. QRコードを出す。
   - 文字のQRを作る: `npx --yes qrcode "<URL>" --small | sed 's/\x1b\[[0-9;]*m//g'`（色コードを消して、文字だけにする。`-t utf8` は `-o` が必要でエラーになるので使わない）
   - 出力された文字を、**返事の本文のコードブロック（```）の中にそのまま貼る**。Bashの出力は崩れて見えることがあるので、ツールの出力だけで済ませない。
   - 暗い背景のターミナルで読み取れないときに備え、画像も保存する: `npx --yes qrcode "<URL>" -o <スクラッチパッド>/kokai-qr.png`（リポジトリに入れない。保存先はフルパスで伝える）
4. 「スマホのカメラで読み取ってください」と伝える。

## 注意

- 秘密のチェックを飛ばさない。okをもらう前に公開しない。
- ユーザーの許可なく `.env` の中身を表示しない（名前が存在するかだけ報告する）。
